## Findings

### Blocker

None.

### Major

- **M1. Delete backup and requeue can permanently delete a backup that is not a copy of the comic.** The action proved only that the *comic* is unchanged (size, mtime and hash against the plan's before state); it never compared the *backup's* bytes, and a skipped or failed comic was not zip-tested. Repro on the tested build, page and routes: a comic unchanged since planning, plus a kept backup that is a valid but different, older version (hash `d8b8a66c…` against comic `0bd4cf4c…`). Check says "A recovery backup is kept. The comic is exactly as it was before the write, so there is nothing to undo." and offers the button; the confirm repeats it; Delete and requeue removes the backup and the folder; nothing is recoverable (Recycle Bin 0). Same with 3 comics, and with a damaged zip in `skipped.json` whose only good copy is the backup. A realistic way to get there: an earlier write was verified but its backup could not be deleted (the 0.2.2 sharing violation family), then a later batch on the same comic was interrupted. Fixed in `93d031f` (backup SHA-256 must equal the plan's before-hash, at the offer, before the first delete and again under the write guard; skipped or failed comics with a backup get the zip test); verified above on a snapshot, not on a build. Senua filed the same as M1; this is the behavioural reproduction. **Status: closed on the rebuilt installer, see "Re-check 2026-10-17".**

### Minor

- **m1. `changed` says two things.** Repro: Check, offer shown, delete that backup in Kept backups, then Delete and requeue. Shown: "Nothing was deleted: a comic changed since the check, so its backup is kept. The list below is updated." and an empty list with no offer. The comic did not change and the backup is not kept. A swapped backup folder (junction) gets the same sentence (the data behind the junction was safe). Suggest a code and a sentence for "the backup is no longer there".
- **m2. What Sergei will actually see on a real interruption.** The "verified result" case of the spec (A1, A5, A6) is never offered: `results.json` records no output hash (Ender disclosed it in the commit). The write order is backup copy, then temp archive, then replace: a kill in the middle leaves a backup **and a temp file**, so there is no offer until he deletes the temp file himself (spec A9, not built); a kill just after the replace leaves the new comic, the backup and no result record, so he gets "Does not match the file this batch planned." plus "Do not delete it until the comic is checked." and only Check, Open folder and Show in folder. As specified, but worth telling Sergei before he meets it.
- **m3. Copy.** While its own delete runs, the offer button's tooltip says "This folder is being worked on. Wait for it to finish." The spec (A2) says "Deleting the backup, then checking again." (the confirm face has it right).
- **m4. The delete route does not re-check the offer rule.** A hand-made request with ids from a check that had a leftover temp file (so no offer) deleted the backup (`not_requeued`, deleted 1). Not reachable from the page; reachable by a race (a temp file appears after the check).
- **m5. "Due" means the comic records, not the folder.** The close moves the comics' retry time to now; the folder's own `next_scan` is unchanged (1792188436.9 before and after). The write came at the folder's next pass: 4 s when the folder was already due, up to the folder interval (about 10 minutes) plus its queue position in a running library. The copy ("at the next folder pass") is true; the brief's wording "the folder becomes due" is not what the code does.
- **m6. Pre-existing, found by accident: an open ticket with a missing or unreadable plan stops every folder pass.** `coverage_priority.pending_paths()` opens every `needs_attention` ticket's plan; a bad one makes each pass fail ("[Errno 2] … 'nope'") and retry only after about 10 minutes, until the ticket is closed. My malformed fixture tickets did this for about 10 minutes. 0.2.5's **Close and recheck folder** is the cure, but it cannot be used when the folder itself is unavailable (`folder_unavailable`), so a ticket with an unreadable plan **and** a deleted folder stays stuck until its file is removed by hand. Not in the 0.2.5 diff.
- **m7. 160 CSS px.** As classified above: accepted last resort. The page overflow at 320 is the `#roots` path (pre-existing, P3).
- **m8. Nit.** With a Close offer and more than 20 changed comics the line says "1 more not shown. Fix these first, then check again." while the summary says to close the item.
- **m9. Nit.** After a partial delete the list keeps the row of the backup that was deleted (a snapshot, as specified); its Show in folder would answer "File not found".
- **m10. Pre-existing, unchanged since 0.2.0 or 0.2.4.** The empty shell notice bar is always visible under the header (`.shell-notice{display:flex}` overrides `hidden`; 56 px blue empty box); malformed request bodies answer with Python's parser text; PUT, DELETE and HEAD on API paths answer a stock 501 HTML page; ticket ids match case-insensitively on Windows (`C14D` reached `c14d`; harmless, same file).
- **Not a finding.** A ticket whose folder is stored with a `\\?\` prefix answers `plan_unreadable` (safe); the app never writes one.
